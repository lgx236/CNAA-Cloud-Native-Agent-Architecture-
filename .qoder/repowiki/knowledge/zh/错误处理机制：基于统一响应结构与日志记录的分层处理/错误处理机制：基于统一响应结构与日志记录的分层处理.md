该仓库采用轻量级的分层错误处理模式，未定义专用异常类型或全局错误码体系，而是通过统一的 JSON 响应结构和 Python 标准库的 try/except + logging 实现错误捕获与传播。

**1. 系统与方法**
- 使用 Python 内置 `try/except` 进行异常捕获，未使用自定义异常类或第三方错误框架。
- 所有 HTTP 层和 MCP 工具调用层均返回统一的 JSON 结构：成功时 `{"status": "ok", ...}`，失败时 `{"status": "error", "message": str(e)}`，资源不存在时 `{"status": "not_found", "message": ...}`。
- 通过 Python 标准库 `logging` 模块记录错误堆栈，未集成结构化日志框架。

**2. 关键文件与位置**
- `server.py`: HTTP 请求处理器，负责解析 JSON、路由到 MCP 服务、捕获 `json.JSONDecodeError` 和通用 `Exception`，并通过 `_send_error` 方法返回统一错误响应。
- `cloud/server/mcp_server.py`: MCP 服务器核心，`handle_tool_call` 方法通过 try/except 包裹所有工具处理器，对未知工具返回 error 状态，对异常记录日志并返回 message。
- `local/client/mcp_client.py`: 客户端侧在连接失败时返回 `{"status": "error", "message": "MCP client not connected to server"}`。
- `tests/test_integration.py`: 测试用例验证了 unknown tool、not found 等错误场景的预期行为。

**3. 架构与约定**
- **分层错误处理**：HTTP 层（server.py）→ MCP 路由层（mcp_server.py.handle_tool_call）→ 具体工具处理器，每层都捕获异常并转换为统一 JSON 响应。
- **状态码映射**：HTTP 层使用 `http.HTTPStatus`（如 `BAD_REQUEST=400`、`INTERNAL_SERVER_ERROR=500`、`NOT_FOUND=404`），MCP 应用层使用字符串状态（`"ok"`、`"error"`、`"not_found"`）。
- **错误信息传递**：异常对象通过 `str(e)` 转换为字符串消息，未保留原始异常类型或堆栈信息给客户端。
- **日志记录**：使用 `logger.exception()` 记录完整堆栈，但仅用于服务端调试，不暴露给客户端。

**4. 约定与约束**
- 所有工具处理器必须返回包含 `status` 字段的字典，这是 MCP 协议的隐式契约。
- 未找到资源时使用 `"not_found"` 状态而非抛出异常，由调用方判断业务逻辑。
- 未知工具名直接返回 error 状态，不进行进一步处理。
- 客户端在未设置 mock handler 时返回特定错误消息，便于开发调试。
- 存储层（memory_store.py、state_store.py）不抛出异常，操作失败时返回 `{"status": "ok"}` 或 None，由上层处理空值情况。
